VolCast: reading the code

How the repository turns minute-by-minute SPY prices into a test of five volatility forecasts, what each part does, and where the test is less fair than it looks.

How to use this

Sections follow execution order, from raw Parquet files to the scoreboard. Every code snippet comes from src/volcast/. Every number in a grey Sample data box came from the repository's checked-in data on 2026-08-10; none is an estimate. Coloured boxes mark design choices, traps, and weaknesses.

The process in plain English

Volatility measures how much a price moves. This project measures SPY's daily movement from minute prices, then asks five models to forecast it for tomorrow and the following week. Each model sees only the past, is refitted every 21 trading days, and is scored on 286 days it never trained on. The scoreboard ranks the forecasts; a statistical test checks whether a gap between two models is large enough to treat as meaningful.

01What is where — folders and entry points

The package lives under src/volcast/ and is organised by job, not file type. Only code under src/ is importable product code.

FolderWhat lives thereDepends on

data/Stage 1: validates the raw Parquet cache and can refresh it from the databaseshared/

evaluation/Stage 4: walk-forward loop, loss functions, and statistical testsfeatures/, models/, shared/

Entry points

# the normal route: runs stages 2, 3, 4 in order
uv run python -m volcast.pipeline.run_pipeline

# --from picks the first stage to run; default is 2 (offline)
uv run python -m volcast.pipeline.run_pipeline --from 1 --force

# each stage is also a standalone command
uv run python -m volcast.features.compute_rv
uv run python -m volcast.features.build_features
uv run python -m volcast.evaluation.train_evaluate
What it does

Input: two command-line flags, --from and --force. Output: four parquet files in outputs/. Role: run_pipeline.main() holds a list of (stage name, function) pairs, skips any stage numbered below --from, and times each one.

Why the stage imports sit inside the functions

Each run_stage_N function imports its stage module on the line that uses it, not at the top of the file. Stage 1 imports clickhouse_connect, a database driver. Putting that import at module level would mean that anyone running only stages 2 to 4 still needs a working database driver installed. Deferring the import keeps the offline path free of that requirement.

02Settings — config.toml and shared/

There is one settings file. Every stage reads it through load_config(), which finds it from the source file's location rather than the working directory:

PROJECT_ROOT = Path(__file__).resolve().parent.parent.parent.parent
# src/volcast/shared/paths.py -> shared -> volcast -> src -> project root
Why paths are derived, not hard-coded

The four .parent hops start at the file itself, so every command works the same from the project root, notebooks/, or any other directory. The package never calls os.getcwd().

Trap: two settings are read by nothing

rv.estimators and rv.target_estimator appear in config.toml, but no code under src/ reads them. All three variance estimators are always computed, and the target is always rv_cc, written directly in compute_rv._add_forecast_targets. Changing target_estimator = "parkinson" does nothing.

Trap: rv.har_lags is not really adjustable

add_har_lags names columns from the fixed map {1: "d", 5: "w", 22: "m"} and uses the number itself for any other lag. FEATURE_COLS then expects rv_cc_d, rv_cc_w, and rv_cc_m. Setting har_lags = [1, 10, 30] would create rv_cc_10 and rv_cc_30, after which stage 3 would fail because the expected columns are missing. Use [1, 5, 22].

03Stage 1 — the cache contract

Stage 1 is optional and skipped by default. It checks whether the Parquet data in data/raw/ matches what the project expects. If it does, nothing happens. If it does not and ClickHouse is reachable, only the broken datasets are fetched again.

Each Parquet file has a companion JSON file, such as SPY_minutes.parquet.metadata.json. validate_cache_spec checks that the files exist and parse, the options cache is a directory of shards, the metadata keys are exact, the cache version, dataset name, file name, columns, and requested dates match, and the Parquet columns, row count, and first and last dates match.

What it does

Input: a CacheSpec for one dataset and the cache folder. Output: a (is_valid, reason) pair; the reason names the file and mismatch. Role: stops stale data from being mixed into the benchmark without notice.

Not run for this page

Stage 1's refresh path needs a ClickHouse database that is not available here, so it was not executed and has no sample output. Its validation path is covered by tests/test_fetch_data_cache.py, which passes. Everything else on this page was run.

04Stage 2 — measuring realised variance

This stage measures how much the price moved. It takes 454,835 SPY minute bars and returns one row per trading day.

close_to_close_rv — add up the squared minute moves

def close_to_close_rv(closes: np.ndarray) -> float:
    if closes.size < 2:
        return 0.0

    # Intraday log returns: r_i = log(C_i / C_{i-1}).
    log_returns = np.diff(np.log(closes))

    # Daily realised variance proxy: RV = sum_i r_i^2.
    realised_variance = np.sum(log_returns**2)
    return float(realised_variance)
In plain words

Square each minute's price change so gains and losses both count, then add the results. A calm day has a small value; a volatile day has a large one.

What it does

Input: one day's minute closing prices as an array. Output: the day's realised variance, a single number. Role: this becomes the rv_cc column and, shifted forward, the target every model predicts.

The formula

$$RV_t=\sum_{i=1}^{m_t} r_{i,t}^{2},\qquad r_{i,t}=\log\frac{C_{i,t}}{C_{i-1,t}}$$

$RV_t$ is realised variance on day $t$. $C_{i,t}$ is the closing price of minute bar $i$ on day $t$. $r_{i,t}$ is that bar's log return. $m_t$ is the number of kept minute bars on day $t$; the sample has 911 on the first day. The sum covers minutes within the day, so it excludes the overnight price jump.

Trap: these are extended-hours bars

The timestamps run from 04:00 to 19:59, not 09:30 to 16:00, so they include pre-market and after-hours trading. daily_close is therefore the 19:59 price, not the official 16:00 close, and daily_open is the 04:00 price. The code is consistent; "close-to-close" does not mean exchange close here.

parkinson_rv and garman_klass_rv — range-based estimates

The formulas

Parkinson uses only the day's high and low:

$$RV^{\text{PK}}_t=\frac{1}{4\log 2}\left(\log\frac{H_t}{L_t}\right)^{2}$$

Garman-Klass adds the open-to-close move:

$$RV^{\text{GK}}_t=\frac{1}{2}\left(\log\frac{H_t}{L_t}\right)^{2}-(2\log 2-1)\left(\log\frac{C_t}{O_t}\right)^{2}$$

$H_t$, $L_t$, $O_t$, and $C_t$ are the day's high, low, open, and close from the minute bars. $\log$ is the natural logarithm. The constant $1/(4\log 2)\approx 0.3607$ makes the Parkinson estimate unbiased for a random walk without drift; $2\log 2-1\approx 0.3863$ serves the same purpose in Garman-Klass. Both estimates measure daily variance in the same units as $RV_t$.

Why three estimators instead of one

Only rv_cc is the forecast target. The other two are extra predictors, or model inputs. They measure the same quantity differently; the range-based estimates are less sensitive to one outlier minute, so they add some different information about the day's movement.

Trap the Garman-Klass code avoids

Subtracting terms can produce a negative variance. It does not here: the daily range covers the open-to-close move, so $|\log(H/L)| \ge |\log(C/O)|$, and $0.5 x^{2}$ is larger than $0.3863 x^{2}$. The result is non-negative for every valid bar.

add_har_lags — yesterday, last week, last month

    for lag_window in lags:
        lag_suffix = suffix_by_lag.get(lag_window, str(lag_window))
        lag_column_name = f"{column}_{lag_suffix}"

        if lag_window == 1:

        lagged_df[lag_column_name] = rolling_mean
In plain words

For each day, record yesterday's value, the average of the last five days, and the average of the last twenty-two days. These are roughly yesterday, last week, and last month.

What it does

Input: a daily frame and a variance-column name. Output: the same frame with three columns ending in _d, _w, and _m. Role: these nine columns (three estimators times three windows) make up most of the model input.

The formula

$$x^{(d)}_t=RV_{t-1},\qquad x^{(w)}_t=\frac{1}{5}\sum_{j=1}^{5}RV_{t-j},\qquad x^{(m)}_t=\frac{1}{22}\sum_{j=1}^{22}RV_{t-j}$$

$x^{(d)}_t$, $x^{(w)}_t$, and $x^{(m)}_t$ are the daily, weekly, and monthly inputs on row $t$. Every sum stops at $t-1$, so day $t$ never enters its own inputs. That is why .shift(1) comes before the rolling average. It is the key leakage safeguard in this file.

_add_forecast_targets — what the models must predict

    # One-day-ahead target: RV_{t+1}.
    result_df["rv_1d_ahead"] = result_df["rv_cc"].shift(-1)

    # Five-day-ahead target: mean(RV_{t+1}, ..., RV_{t+5}).
    forward_shifted = result_df["rv_cc"].shift(-1)

The formula

$$y_{t,1}=RV_{t+1},\qquad y_{t,5}=\frac{1}{5}\sum_{j=1}^{5}RV_{t+j}$$

$y_{t,1}$ is tomorrow's realised variance attached to row $t$. $y_{t,5}$ is the average daily variance over the next five trading days, not their sum or the variance of the five-day return.

Why the five-day target needs two shifts

The first shift(-1) puts $RV_{t+1}$ on row $t$. The rolling five-day mean on row $t$ covers rows $t-4$ to $t$ and, after the shift, holds $RV_{t-3}$ through $RV_{t+1}$. It ends in the right place but starts four days early. The final shift(-4) moves the window forward, so row $t$ receives the value computed on row $t+4$: the mean of $RV_{t+1}$ through $RV_{t+5}$. The sample below checks this numerically.

05Stage 3 — building the feature table

Stage 3 joins three sources into one row per trading day: stage-2 variance columns, four option-implied columns, and the VIX index. It writes data/processed/SPY_features.parquet.

build_option_features — reading the option market

In plain words

Option prices contain the market's forecast of future volatility. For each day, the code selects three readings from thousands of contracts: expected volatility, the extra price of downside protection, and the difference between near- and later-dated volatility.

What it does

Input: an option-chain table with trade_date, expiry_date, option_type, delta, bid_iv, and ask_iv. Output: one row per trade date with atm_iv, iv_skew, and iv_term_slope. Role: three of the fourteen model inputs.

The three readings

$$\mathrm{atm\_iv}_t=\frac{\mathrm{bid\_iv}+\mathrm{ask\_iv}}{2}\ \text{ for the call with } \arg\min_k\left|\delta_k-0.50\right|$$

$$\mathrm{iv\_skew}_t=\sigma^{\text{put}}_{\delta=-0.25}-\sigma^{\text{call}}_{\delta=+0.25}$$

$$\mathrm{iv\_term\_slope}_t=\sigma^{\text{atm}}_{\text{second expiry}}-\sigma^{\text{atm}}_{\text{front expiry}}$$

$\sigma$ is implied volatility: the annual volatility that makes an option-pricing model match the quoted price. Thus 0.165 means 16.5 per cent a year. $\delta_k$ is contract $k$'s delta, the change in option price per dollar of underlying-price change; a call with $\delta=0.50$ is roughly at-the-money. "Front expiry" is the nearest date that passes the days-to-expiry filter; "second expiry" is the next one. All three readings use the bid-ask midpoint, so a wide quote does not push them up or down.

The timing rules — where look-ahead is prevented

def _lag_trade_date_feature_frame(feature_df: pd.DataFrame, date_col: str) -> pd.DataFrame:
    """Shift feature date one business day forward to enforce t-1 feature usage."""
    lagged_df = feature_df.copy()
    lagged_df["date"] = pd.to_datetime(lagged_df[date_col]) + pd.offsets.BDay(1)
    lagged_df = lagged_df.drop(columns=[date_col])
    lagged_df = lagged_df.sort_values("date").reset_index(drop=True)
    return lagged_df
In plain words

An option chain observed on Monday is assigned to Tuesday. When the model uses Tuesday's row, the information was available before Tuesday began.

The IV-RV spread

$$\mathrm{iv\_rv\_spread}_t=\mathrm{atm\_iv}_t-\sqrt{252\,x^{(w)}_t}$$

$x^{(w)}_t$ is the daily variance from the five-day average in stage 2. Multiplying by 252 trading days annualises the variance; taking the square root gives annual volatility, which can be compared with annual atm_iv. A positive spread means options are priced above recent realised movement. On the first row, $0.27515-\sqrt{252\times0.000209}=0.27515-0.229757=0.045393$, matching the stored value 0.045393163676948844.

Why business-day shift and forward filling are both needed

BDay(1) moves a Friday chain to Monday but does not know market holidays. If Monday is a holiday, Tuesday's row is empty. The following ffill(limit=3) carries the latest reading across up to three gaps. Because it only moves information forward, it makes a value staler, not fresher; it cannot use future information.

Trap: the spread is filled, not recomputed

iv_rv_spread is computed before the forward fill and is then forward-filled itself. On a gap day, the value is yesterday's complete spread: yesterday's atm_iv paired with yesterday's weekly realised variance. It is stale in a different way from the neighbouring columns. This does not create leakage, but it explains an unexpected value.

06The five models and their formulas

All five use the same two-method interface from models/base.py: fit(X, y) followed by predict(X). Each clips its output at MIN_POSITIVE_VARIANCE = 1e-10, because QLIKE is undefined for a zero or negative variance forecast.

HAR-RV — the academic benchmark

The formula

$$\widehat{y}_{t}= \beta_0+\beta_d\,x^{(d)}_t+\beta_w\,x^{(w)}_t+\beta_m\,x^{(m)}_t$$

$\widehat{y}_t$ is the forecast variance for row $t$. $x^{(d)}_t$, $x^{(w)}_t$, and $x^{(m)}_t$ are the daily, weekly, and monthly lagged realised variances from stage 2. $\beta_0$ is the intercept; $\beta_d$, $\beta_w$, and $\beta_m$ are slopes. Ordinary least squares fits all four by minimising $\sum_t (y_t-\widehat{y}_t)^2$ on the training rows. HAR means Heterogeneous Autoregressive: it combines daily, weekly, and monthly histories. The code uses only the three rv_cc columns (HAR_FEATURES), not the other eleven predictors.

GARCH(1,1) — the volatility-clustering benchmark

            one_step_variance = (
                omega_decimal + self._alpha * observed_return**2 + self._beta * previous_variance
            )

            # For k>1, E_t[r_{t+k-1}^2] equals its conditional variance, so the
            # expected variance recursion uses persistence = alpha + beta.
            horizon_variance = one_step_variance
            variance_sum = one_step_variance
            for _ in range(1, self._forecast_horizon):
                horizon_variance = omega_decimal + persistence * horizon_variance
                variance_sum += horizon_variance

            average_variance_forecasts[row_index] = variance_sum / self._forecast_horizon
            previous_variance = one_step_variance
The formula the code implements

The model of daily return variance:

$$h_{t+1}=\omega+\alpha r_t^{2}+\beta h_t$$

Stepping further ahead, with $\phi=\alpha+\beta$:

$$h_{t+k}=\omega+\phi\,h_{t+k-1},\qquad k=2,\dots,H$$

And the forecast the code returns, matching the averaged target:

$$\widehat{y}_{t}=\frac{1}{H}\sum_{k=1}^{H}h_{t+k}$$

$h_{t}$ is the conditional variance for day $t$: the variance expected from information available through day $t-1$. $r_t$ is that day's log return on day $t$. $\omega$ is a constant floor, $\alpha$ controls the effect of the latest return shock, $\beta$ controls how much prior variance carries over, and $\phi=\alpha+\beta$ is persistence, or how slowly a volatility burst fades. $H$ is the forecast horizon, 1 or 5. GARCH means Generalized Autoregressive Conditional Heteroskedasticity; heteroskedasticity means that variance changes over time.

Why the code multiplies returns by 100 and then divides by 10,000

fit passes returns * 100 to the arch library. Optimisers behave poorly when inputs are around 0.01, so percentage points put them around 1. Variance scales with the square of the input; returned variances are divided by $100^2=10{,}000$ to restore decimal units. Missing either conversion makes the forecasts wrong by a factor of ten thousand.

Ridge and Lasso — penalised linear models in log space

The formula

Both fit a straight line to the logarithm of variance using all fourteen predictors after standardising each one:

$$\log y_t \approx \gamma_0+\sum_{j=1}^{14}\gamma_j z_{j,t}, \qquad z_{j,t}=\frac{x_{j,t}-\bar{x}_j}{s_j}$$

Ridge chooses the coefficients by minimising

$$\sum_t\Big(\log y_t-\gamma_0-\sum_j \gamma_j z_{j,t}\Big)^{2}+\lambda\sum_j \gamma_j^{2}$$

Lasso replaces the penalty with the sum of absolute values:

$$\sum_t\Big(\log y_t-\gamma_0-\sum_j \gamma_j z_{j,t}\Big)^{2}+\lambda\sum_j \left|\gamma_j\right|$$

and the prediction is mapped back with

$$\widehat{y}_t=\max\left(e^{\widehat{\log y_t}},\,10^{-10}\right)$$

$x_{j,t}$ is predictor $j$ on row $t$; $\bar{x}_j$ and $s_j$ are its training mean and standard deviation, so $z_{j,t}$ is the standardised value. $\gamma_j$ are the fitted coefficients and $\gamma_0$ is the intercept. $\lambda$ controls the penalty and is selected from 40 candidates by RidgeCV or LassoCV with TimeSeriesSplit. Validation always uses data later than the training data. The squared penalty shrinks coefficients; the absolute-value penalty can set some to zero, so Lasso also selects variables.

Trap: fitting in logs shifts what is being predicted

Fitting $\log y$ and then taking $e^{\widehat{\log y}}$ does not estimate the average of $y$. It gives roughly the median of $y$, which is below the mean for a right-skewed quantity such as variance. That helps explain why Ridge and Lasso top the QLIKE table but sit at the bottom of the MSE table: QLIKE rewards a good typical-day forecast, while MSE is driven by the few turbulent days they under-forecast.

XGBoost — the nonlinear entry

What it does

Input: all fourteen predictors, without scaling or transformation. Output: a variance forecast floored at $10^{-10}$. Role: a gradient-boosted decision-tree model that can capture relationships a straight line cannot. Its source settings are fixed: 200 trees, maximum depth 4, learning rate 0.05, and at least 10 rows per leaf.

It does not do what it appears to do

On this data XGBoost builds no splits at all. The limitations section shows the measurements.

07Stage 4 — walk-forward evaluation

This function controls the benchmark's timing. It moves forward through time: train on the past, forecast the next block, move the boundary, and repeat.

    # The target for feature row i averages realised variance over the horizon
    # trading days after i. Rows within horizon-1 of the first test date therefore

    # the training slice. For horizon=1 nothing is purged.

        train_df = working_df.iloc[: retrain_idx - purged_train_rows]
In plain words

Hold back the first year. Fit on everything before the boundary, forecast the next 21 trading days, move the boundary 21 days forward, and refit on the larger history. The training window grows and never includes a forecast day.

What it does

Input: the 537-row feature table, a symbol, a horizon, and the config. Output: a long table with one row per date and model containing y_true and y_pred. Role: all later scores, tests, and diagnostics read this table.

The purge, stated precisely

Training row $i$ carries $y_{i,H}=\frac{1}{H}\sum_{j=1}^{H}RV_{i+j}$, which is complete on day $i+H$. Let $T$ be the first forecast date. A training row is safe only if its label was complete by $T$:

$$i+H\le T \iff i\le T-H$$

Therefore rows $T-H+1,\dots,T-1$ must be removed: exactly $H-1$ rows.

$H$ is the trading-day horizon, 1 or 5. $T$ is the index of the first test row. For $H=1$, nothing is removed. For $H=5$, four rows are removed from every training window. Otherwise, five-day labels would contain realised variance from days the model is about to forecast.

Why the minimum training size adds the purged rows back

The code uses MIN_TRAIN_OBS + purged_train_rows, not just MIN_TRAIN_OBS, so 25 rows reach the model after the purge. Since $H-1$ rows are removed after the boundary is chosen, the boundary must sit $H-1$ rows later to leave 25 behind. It also keeps retrain_idx - purged_train_rows positive.

At horizon 1, the first model uses rows 0 to 250 and forecasts rows 251 to 271. At horizon 5, it uses rows 0 to 246—four rows fewer—and forecasts the same 21 dates. Each model produces 286 forecasts at each horizon, so forecasts.parquet has $5\times2\times286=2{,}860$ rows.

Trap: a failing model becomes a silent row of NaN

except Exception catches errors from fit and predict. The error is logged at warning level and the block becomes NaN. A model that fails on some blocks therefore looks like a model with fewer observations, and compute_scores skips one with fewer than 10 valid rows. A fully broken model disappears from the scoreboard. Check n_obs and the log.

08Scoring — QLIKE, MSE, Diebold-Mariano

The two loss functions

The formulas the code implements

Mean squared error, from mse_loss:

$$\text{MSE}=\frac{1}{n}\sum_{t=1}^{n}\left(y_t-\widehat{y}_t\right)^{2}$$

Quasi-likelihood loss, from qlike_loss:

$$\text{QLIKE}=\frac{1}{n}\sum_{t=1}^{n}\left[\log\widehat{y}_t+\frac{y_t}{\widehat{y}_t}\right]$$

$y_t$ is realised variance on scored date $t$ and $\widehat{y}_t$ is the forecast; both are strictly positive. $n$ is the number of scored dates, 286 here. Lower is better. The code does not include the textbook QLIKE terms $-\log y_t - 1$, which would make the minimum zero. They do not depend on the forecast, so rankings stay the same, but the printed QLIKE values near $-8.8$ are meaningful only within this project.

Why QLIKE is the primary score for variance

Mean squared error (MSE) uses squared variance units. Here daily variance is around $10^{-4}$, so squared errors are around $10^{-9}$ and a few turbulent days dominate. Quasi-likelihood loss (QLIKE) uses the ratio $y_t/\widehat{y}_t$, so a forecast twice too high has the same ratio on a calm or volatile day. It also penalises under-forecasting more than over-forecasting.

Sample data
in — HAR-RV, first scored date 
date    2023-11-02

The forecast was 1.75 times the realised value, so the model was too high that day. Across 286 days, HAR-RV scores $-8.797168$, matching the qlike value in scores.parquet.

diebold_mariano_test — is the gap real?

In plain words

Model A beat model B on average. Forecast errors can still move together from day to day, so luck can look like skill. This test compares the average gap with the amount that gap varies.

The formula the code implements

Let $d_t=L^A_t-L^B_t$ be the difference in QLIKE loss on date $t$, and $\bar{d}$ its average. The long-run variance uses Bartlett-weighted autocovariances:

$$\widehat{\gamma}_k=\frac{1}{n}\sum_{t=k+1}^{n}(d_t-\bar{d})(d_{t-k}-\bar{d})$$

$$\widehat{V}=\widehat{\gamma}_0+2\sum_{k=1}^{K}\left(1-\frac{k}{K+1}\right)\widehat{\gamma}_k, \qquad K=\max\left(1,\left\lfloor n^{1/3}\right\rfloor\right)$$

$$\text{DM}=\frac{\bar{d}}{\sqrt{\widehat{V}/n}},\qquad p=2\left[1-\Phi(\left|\text{DM}\right|)\right]$$

$L^A_t$ and $L^B_t$ are the two models' daily QLIKE losses. $n$ is the number of common dates, 286 here. $\widehat{\gamma}_k$ is the autocovariance of the loss difference at lag $k$: how much today's gap resembles the gap $k$ days earlier. $K$ is the number of included lags; at $n=286$ it is 6. The Bartlett weights $1-k/(K+1)$ taper to zero, keeping $\widehat{V}$ non-negative. $\Phi$ is the standard normal cumulative distribution function. A positive DM statistic means model A has the higher average loss and is therefore worse.

Why the autocovariance terms are needed at all

If daily losses were independent, $\widehat{\gamma}_0/n$ would be enough. They are not: volatility clusters, so a model that is too low today is often too low tomorrow. Ignoring this would understate the standard error and make p-values too small. The Bartlett-weighted sum corrects for that dependence.

13Honest limitations

XGBoost is not really in the contest

On this data, XGBoost fits zero splits. In the first training block, all fourteen feature importances are 0.0, and the model returns 0.00010017 for all 21 test rows—almost the training-target mean of 0.00009958. Across 286 forecast dates, there are only 14 distinct predictions, one per retrain block.

The target is too small. Daily variance is around $10^{-4}$, so XGBoost's split gains fall below the threshold for growing a tree. Multiplying the target by 100 or more makes the same model use all fourteen features and produce 20 distinct predictions per block:

target scale    1e+00: unique preds  1/21, features used  0/14, pred std 0.000e+00
target scale    1e+02: unique preds 20/21, features used 14/14, pred std 1.241e-05
target scale    1e+04: unique preds 20/21, features used 14/14, pred std 1.234e-05
target scale    1e+06: unique preds 20/21, features used 14/14, pred std 1.234e-05

Read the result carefully. "XGBoost is significantly worse than HAR-RV, Ridge and Lasso at $p<0.0001$" does not show that gradient boosting is worse. It shows that those models beat a constant. The code leaves this unchanged because scaling or log-transforming the target would change the benchmark result. The one-line change would give XGBoostModel the log-target transform already used by RidgeModel and LassoModel.

GARCH fits alpha to zero and becomes nearly flat

On the first training block, the fitted parameters are $\omega=0.014878$, $\alpha=0.000000$, and $\beta=0.973339$. With $\alpha=0$, the model does not react to individual return shocks; it is a slowly decaying average with persistence 0.973. Its first-eight-day forecasts move from 0.00005604 to 0.00005600. Across 286 days, they range from 0.000038 to 0.000134, versus HAR-RV's 0.000036 to 0.000249. This is the optimiser's result on roughly one year of daily returns, not a coding error, but the GARCH forecast is closer to a slowly changing constant than to the textbook volatility-clustering model.

The models do not all see the same information

Every stage-3 predictor is lagged to day $t-1$: HAR columns use .shift(1), while options and VIX move forward one business day. On row $t$, HAR-RV, Ridge, Lasso, and XGBoost forecast $RV_{t+1}$ without information after day $t-1$—effectively a two-day-ahead forecast with a one-day label.

GARCH is different. Its predict loop uses daily_returns from row $t$, so it forecasts $RV_{t+1}$ knowing the day-$t$ return. That is not look-ahead: the day-$t$ return is known at the day-$t$ close, before $RV_{t+1}$ occurs. It is, however, one extra day of information that the other four models do not receive, which gives GARCH a small advantage. Removing that advantage would change the benchmark numbers, so the code documents it.

The bandwidth rule can be too small for the five-day test

Five-day targets overlap: consecutive rows share four days, so loss differences are autocorrelated through lag 4. A Diebold-Mariano test needs at least $H-1=4$ lags for that overlap. The code uses $K=\lfloor n^{1/3}\rfloor$; at $n=286$, this gives 6. At $n=30$, the minimum tested here, it gives $K=3$, which is too few and would make p-values too small. The shipped configuration is safe; shorter samples are not.

One asset, 286 days, and no transaction costs

The benchmark uses SPY over roughly fourteen out-of-sample months and one volatility regime. robustness_symbols exists but is empty. The ranking may not hold for another asset, period, or stress episode. The Diebold-Mariano table already finds most pairs indistinguishable at this sample size.

One worry that measured smaller than expected

The target uses intraday minute returns and omits the overnight price jump; GARCH uses close-to-close daily returns and includes it. In principle, GARCH therefore forecasts a larger quantity than the scored target. Here the gap is small: mean rv_cc is 8.556844e-05, while daily-return variance is 8.518606e-05, a ratio of 0.9955. The minute bars cover 04:00 to 19:59, so little movement remains outside the window. Recheck this if the source changes to regular trading hours only.

14Fixes applied

Three changes were made to src/volcast/evaluation/train_evaluate.py. No other source file was modified. The full suite of 56 tests passes before and after.

1. Purge overlapping targets from the training window

The bug

At horizon 5, the training window reached the first forecast date. The last four training rows contained targets that averaged realised variance from days inside the forecast block. Those labels were not available at the forecast origin, so the fit used future information. This look-ahead bias affected only horizon 5.

# before
train_df = working_df.iloc[:retrain_idx]

# after
purged_train_rows = horizon - 1
train_df = working_df.iloc[: retrain_idx - purged_train_rows]

The minimum boundary was raised to MIN_TRAIN_OBS + purged_train_rows so 25 rows still reach the model after the purge and the slice index cannot go negative. Horizon 1 is unchanged because $H-1=0$.

2. Advance the GARCH variance state up to the forecast date

The bug

GARCHModel.predict starts its recursion with the last fitted conditional variance. The loop needs $h_t$ for the first row it receives, but it received $h_T$, the variance of the last training row. These are one row apart at horizon 1 and, after fix 1, five rows apart at horizon 5. Every retrain block started from a stale state.

A simulated GARCH series confirmed the alignment. The reconstruction $\omega+\alpha r_{T-1}^{2}+\beta h_{T-1}$ matches conditional_volatility[-1] to sixteen digits; using $\omega+\alpha r_{T}^{2}+\beta h_{T-1}$ does not. The library's $h_t$ is indexed to day-$t$ return, so the code needed one more update.

# before
return model.predict(test_df[garch_columns]), model.name

# after: feed the last training row and any purged rows as warm-up,
# then keep only the tail that lines up with test_df
state_predictions = model.predict(garch_state_df[garch_columns])
return state_predictions[-len(test_df) :], model.name

The caller builds the warm-up frame because it knows the row indices:

last_train_idx = retrain_idx - purged_train_rows - 1
garch_state_df = working_df.iloc[last_train_idx:test_end]

Only GARCH's numbers changed: horizon 1 QLIKE went from $-8.761820$ to $-8.762988$; horizon 5 went from $-8.753833$ to $-8.752250$. The change is small because the one-step correction decays at $\beta=0.97$, but the state is now aligned.

3. Read the Diebold-Mariano model list off the pivot table

The bug

compute_dm_tests took model names from the raw forecast table and looked them up in a pivot table. If a model failed at every retrain point, its forecasts were all NaN, pivot_table dropped the column, and the lookup raised KeyError. Stage 4 then stopped after computing forecasts but before writing output. The except Exception handler makes this failure reachable whenever a model breaks.

# after: the pivot is the authority on which models actually have forecasts
models = sorted(pivot["y_pred"].columns)
What was deliberately left alone

Nine files have uncommitted formatting-only changes from ruff format: quote style, line wrapping, import order, and two redundant int() calls around len(). Each change was inspected; no needed import was removed, and the tests pass, so none was committed. The limitations in section 13 were documented rather than changed because each would alter the reported ranking. That is a research decision, not a bug fix.
