VolCast: reading the code

How this repository turns minute-by-minute SPY prices into a fair contest between five volatility forecasting models, what each piece does, and where the contest is less fair than it looks.

How to use this

Sections follow execution order, from raw parquet files through to the scoreboard. Every code snippet is copied from the files under src/volcast/. Every number in a grey Sample data box came from running the code on the repository's own checked-in data on 2026-08-10 — none of them are estimates. Coloured boxes flag design choices, traps, and weaknesses.

The process in plain English

Volatility is how much a price jumps around. This project measures how much SPY actually jumped around on each day, using minute-by-minute prices, and then asks five different models to predict how much it will jump around tomorrow, and over the coming week. Each model is only ever allowed to see the past, is refitted every 21 trading days, and is scored on 286 days it never trained on. The scoreboard says which model predicted best, and a statistical test says whether the gap between two models is big enough to believe.

01What is where — folders and entry points

The package lives under src/volcast/ and is organised by job, not by file type. Nothing outside src/ is importable product code.

FolderWhat lives thereDepends on
shared/Config loading, project paths, logging setupnothing
data/Stage 1: raw parquet cache validation and optional database refreshshared/
features/Stages 2 and 3: variance estimators, option features, the feature tableshared/
models/The five forecasters behind one shared interfacenothing in the package
evaluation/Stage 4: walk-forward loop, loss functions, statistical testfeatures/, models/, shared/

Entry points

# the normal route: runs stages 2, 3, 4 in order
uv run python -m volcast.pipeline.run_pipeline

# --from picks the first stage to run; default is 2 (offline)
uv run python -m volcast.pipeline.run_pipeline --from 1 --force

# each stage is also a standalone command
uv run python -m volcast.features.compute_rv
uv run python -m volcast.features.build_features
uv run python -m volcast.evaluation.train_evaluate
What it does

Input: two command-line flags, --from and --force. Output: four parquet files in outputs/. Role: run_pipeline.main() holds a list of (stage name, function) pairs, skips any stage numbered below --from, and times each one.

Why the stage imports sit inside the functions

Each run_stage_N function imports its stage module on the line that uses it, not at the top of the file. Stage 1 imports clickhouse_connect, a database driver. Putting that import at module level would mean that anyone running only stages 2 to 4 still needs a working database driver installed. Deferring the import keeps the offline path free of that requirement.

02Settings — config.toml and shared/

There is exactly one settings file. Every stage reads it through load_config(), which resolves the path from the location of the source file rather than from the working directory:

PROJECT_ROOT = Path(__file__).resolve().parent.parent.parent.parent
# src/volcast/shared/paths.py -> shared -> volcast -> src -> project root
Why paths are derived, not hard-coded

Because the four .parent hops are counted from the file itself, every command works the same whether you launch it from the project root, from notebooks/, or from anywhere else on the machine. There is no os.getcwd() anywhere in the package.

Trap: two settings are read by nothing

rv.estimators and rv.target_estimator appear in config.toml with helpful comments, but a search across src/ finds no code that reads either key. All three variance estimators are always computed, and the forecast target is always rv_cc, written literally into compute_rv._add_forecast_targets. Changing target_estimator = "parkinson" has no effect at all.

Trap: rv.har_lags is not really adjustable

add_har_lags names its output columns from a fixed map, {1: "d", 5: "w", 22: "m"}, and falls back to the number itself for anything else. The feature list FEATURE_COLS then asks for rv_cc_d, rv_cc_w, rv_cc_m by name. Setting har_lags = [1, 10, 30] would silently produce columns called rv_cc_10 and rv_cc_30, and stage 3 would then fail with a missing-column error. The setting only accepts [1, 5, 22].

03Stage 1 — the cache contract

Stage 1 is optional and is skipped by default. Its job is to answer one question: is the parquet data in data/raw/ exactly the data this project expects? If yes, it does nothing. If no, and a ClickHouse database is reachable, it refetches only the broken datasets.

Each parquet file has a companion JSON file beside it, for example SPY_minutes.parquet.metadata.json. validate_cache_spec checks eight things: the parquet exists; the options cache is a directory of shards rather than one file; the sidecar exists and parses; the sidecar has exactly the expected set of keys; the cache version, dataset name, file name, column list, and requested date range all match; the parquet's own columns match in the same order; the row count matches; and the earliest and latest dates match.

What it does

Input: a CacheSpec describing one expected dataset, plus the cache folder. Output: a (is_valid, reason) pair, where the reason is a sentence naming the file and the mismatch. Role: lets the project fail loudly on stale data rather than quietly benchmarking a mixture of two different vintages.

Not run for this page

Stage 1's refresh path needs a ClickHouse database that is not available here, so it was not executed and no sample output is shown for it. Its validation path is exercised by tests/test_fetch_data_cache.py, which passes. Everything else on this page was run.

04Stage 2 — measuring realised variance

This is where "how much did the price actually move" gets a number. The input is 454,835 minute bars for SPY. The output is one row per trading day.

close_to_close_rv — add up the squared minute moves

def close_to_close_rv(closes: np.ndarray) -> float:
    if closes.size < 2:
        return 0.0

    # Intraday log returns: r_i = log(C_i / C_{i-1}).
    log_returns = np.diff(np.log(closes))

    # Daily realised variance proxy: RV = sum_i r_i^2.
    realised_variance = np.sum(log_returns**2)
    return float(realised_variance)
In plain words

Take every minute's price change during the day, square each one so that ups and downs both count as movement, and add them all up. A calm day gives a small number; a wild day gives a big one.

What it does

Input: one day's minute closing prices as an array. Output: a single number, the day's realised variance. Role: this is the rv_cc column, and shifted forward it becomes the thing every model is trying to predict.

The formula

$$RV_t=\sum_{i=1}^{m_t} r_{i,t}^{2},\qquad r_{i,t}=\log\frac{C_{i,t}}{C_{i-1,t}}$$

$RV_t$ is the realised variance on day $t$. $C_{i,t}$ is the closing price of the $i$-th minute bar on day $t$. $r_{i,t}$ is that minute's log return. $m_t$ is the number of minute bars kept on day $t$, which the sample below shows is 911 on the first day. Note that the sum runs over minutes within the day only, so the overnight price jump is not included.

Trap: these are extended-hours bars

The timestamps run from 04:00 to 19:59, not 09:30 to 16:00. The data includes pre-market and after-hours trading, so daily_close is the 19:59 price rather than the official 16:00 close, and daily_open is the 04:00 price. This is not wrong, but it means "close-to-close" in the variable names does not mean the exchange close.

parkinson_rv and garman_klass_rv — range-based estimates

The formulas

Parkinson uses only the day's high and low:

$$RV^{\text{PK}}_t=\frac{1}{4\log 2}\left(\log\frac{H_t}{L_t}\right)^{2}$$

Garman-Klass adds the open-to-close move:

$$RV^{\text{GK}}_t=\frac{1}{2}\left(\log\frac{H_t}{L_t}\right)^{2}-(2\log 2-1)\left(\log\frac{C_t}{O_t}\right)^{2}$$

$H_t$, $L_t$, $O_t$, $C_t$ are the day's high, low, open and close, taken from the minute bars. $\log$ is the natural logarithm. The constant $1/(4\log 2)\approx 0.3607$ makes the Parkinson estimate unbiased for a random walk without drift; $2\log 2-1\approx 0.3863$ plays the same role in Garman-Klass. Both give a variance for the day, in the same units as $RV_t$ above.

Why three estimators instead of one

Only rv_cc is ever used as the forecast target. The other two go in as extra predictors. They measure the same underlying thing through different windows — the range-based ones are less sensitive to a single outlier minute — so they carry slightly different information about how turbulent the day was.

Trap the Garman-Klass code avoids

Subtracting one term from another invites a negative variance. It cannot happen here: the daily range always covers at least the open-to-close move, so $|\log(H/L)| \ge |\log(C/O)|$, and $0.5 x^{2}$ is always larger than $0.3863 x^{2}$. The result is non-negative for every valid bar.

add_har_lags — yesterday, last week, last month

    for lag_window in lags:
        lag_suffix = suffix_by_lag.get(lag_window, str(lag_window))
        lag_column_name = f"{column}_{lag_suffix}"

        if lag_window == 1:

        # Weekly/monthly HAR components: mean of previous k days, shifted by 1.
        shifted_series = lagged_df[column].shift(1)

        lagged_df[lag_column_name] = rolling_mean
In plain words

For each day, record three summaries of how turbulent the recent past was: yesterday on its own, the average of the last five days, and the average of the last twenty-two days. Roughly: yesterday, last week, last month.

What it does

Input: a daily frame and the name of a variance column. Output: the same frame plus three new columns, suffixed _d, _w, _m. Role: these nine columns (three estimators times three windows) are most of the model input.

The formula

$$x^{(d)}_t=RV_{t-1},\qquad x^{(w)}_t=\frac{1}{5}\sum_{j=1}^{5}RV_{t-j},\qquad x^{(m)}_t=\frac{1}{22}\sum_{j=1}^{22}RV_{t-j}$$

$x^{(d)}_t$, $x^{(w)}_t$, $x^{(m)}_t$ are the daily, weekly and monthly predictors attached to row $t$. Every sum stops at $t-1$: the value on day $t$ itself never enters its own row's predictors. This is the .shift(1) applied before the rolling average, and it is the single most important line in the file.

_add_forecast_targets — what the models must predict

    # One-day-ahead target: RV_{t+1}.
    result_df["rv_1d_ahead"] = result_df["rv_cc"].shift(-1)

    # Five-day-ahead target: mean(RV_{t+1}, ..., RV_{t+5}).
    forward_shifted = result_df["rv_cc"].shift(-1)
    forward_five_day_mean = forward_shifted.rolling(window=5, min_periods=5).mean()
    result_df["rv_5d_ahead"] = forward_five_day_mean.shift(-4)
The formula

$$y_{t,1}=RV_{t+1},\qquad y_{t,5}=\frac{1}{5}\sum_{j=1}^{5}RV_{t+j}$$

$y_{t,1}$ is the one-day target attached to row $t$: tomorrow's realised variance. $y_{t,5}$ is the five-day target: the average daily variance over the next five trading days, not their sum and not the variance of the five-day return.

Why the five-day target needs two shifts

The three-step construction is easy to get wrong by one day, so it is worth tracing. shift(-1) puts $RV_{t+1}$ on row $t$. The rolling five-day mean on row $t$ then covers rows $t-4$ to $t$, which after the first shift holds $RV_{t-3}$ through $RV_{t+1}$ — ending in the right place but starting four days too early. The final shift(-4) pulls the window forward so row $t$ receives what was computed on row $t+4$, namely the mean of $RV_{t+1}$ through $RV_{t+5}$. Verified numerically below.

05Stage 3 — building the feature table

Stage 3 joins three sources into one table with one row per trading day: the variance columns from stage 2, four option-implied columns, and the VIX index. The result is data/processed/SPY_features.parquet.

build_option_features — reading the option market

In plain words

Option prices contain the market's own forecast of future volatility. For each day, this picks three readings out of thousands of option contracts: how volatile the market expects things to be, how much more it charges for downside protection than upside, and whether it expects more volatility soon or later.

What it does

Input: an option chain table with columns trade_date, expiry_date, option_type, delta, bid_iv, ask_iv. Output: one row per trade date with atm_iv, iv_skew, iv_term_slope. Role: three of the fourteen model predictors.

The three readings

$$\text{atm\_iv}_t=\frac{\text{bid\_iv}+\text{ask\_iv}}{2}\ \text{ for the call with } \arg\min_k\left|\delta_k-0.50\right|$$

$$\text{iv\_skew}_t=\sigma^{\text{put}}_{\delta=-0.25}-\sigma^{\text{call}}_{\delta=+0.25}$$

$$\text{iv\_term\_slope}_t=\sigma^{\text{atm}}_{\text{second expiry}}-\sigma^{\text{atm}}_{\text{front expiry}}$$

$\sigma$ is implied volatility, the volatility figure that makes an option pricing model reproduce the quoted price; it is quoted as an annual fraction, so 0.165 means 16.5 per cent a year. $\delta_k$ is contract $k$'s delta, how much the option price moves per dollar of underlying move; a call with $\delta=0.50$ is roughly at-the-money. "Front expiry" is the nearest expiry date that survives the days-to-expiry filter, and "second expiry" the next one after it. All three use the midpoint of the bid and ask implied volatility, so a wide quote does not bias the reading up or down.

The timing rules — where look-ahead is prevented

def _lag_trade_date_feature_frame(feature_df: pd.DataFrame, date_col: str) -> pd.DataFrame:
    """Shift feature date one business day forward to enforce t-1 feature usage."""
    lagged_df = feature_df.copy()
    lagged_df["date"] = pd.to_datetime(lagged_df[date_col]) + pd.offsets.BDay(1)
    lagged_df = lagged_df.drop(columns=[date_col])
    lagged_df = lagged_df.sort_values("date").reset_index(drop=True)
    return lagged_df
In plain words

An option chain observed on Monday is stamped as Tuesday's information. That way, when a model looks at Tuesday's row, everything on it was already knowable before Tuesday started.

The IV-RV spread

$$\text{iv\_rv\_spread}_t=\text{atm\_iv}_t-\sqrt{252\,x^{(w)}_t}$$

$x^{(w)}_t$ is the weekly average realised variance from stage 2, a daily variance. Multiplying by 252 trading days converts it to an annual variance, and the square root turns it into an annual volatility, so it can be subtracted from atm_iv, which is already annual. A positive spread means options are priced above what recent realised movement alone would justify. Hand check on the first row: $0.27515-\sqrt{252\times0.000209}=0.27515-0.229757=0.045393$, matching the stored value 0.045393163676948844 exactly.

Why business-day shift and forward filling are both needed

BDay(1) moves a Friday chain to Monday, but it does not know about market holidays. If that Monday is a holiday, no feature row exists to receive the value, and Tuesday's row is left empty. The ffill(limit=3) that follows carries the most recent available reading forward across up to three such gaps. The direction only ever goes forward in time, so a gap makes a feature staler, never fresher — it cannot create look-ahead.

Trap: the spread is filled, not recomputed

iv_rv_spread is computed before the forward fill, and then appears in the list of columns that get forward filled. So on a gap day the filled spread is yesterday's whole spread, which pairs yesterday's atm_iv with yesterday's weekly realised variance, not today's. It is stale in a slightly different way from the columns beside it. Harmless for leakage, but worth knowing if the number ever looks odd.

06The five models and their formulas

All five sit behind the same two-method interface declared in models/base.py: fit(X, y) then predict(X). Every one clips its output at MIN_POSITIVE_VARIANCE = 1e-10, because a variance forecast of zero or below would make the QLIKE score undefined.

HAR-RV — the academic benchmark

The formula

$$\widehat{y}_{t}= \beta_0+\beta_d\,x^{(d)}_t+\beta_w\,x^{(w)}_t+\beta_m\,x^{(m)}_t$$

$\widehat{y}_t$ is the forecast variance for row $t$. $x^{(d)}_t$, $x^{(w)}_t$, $x^{(m)}_t$ are the daily, weekly and monthly lagged realised variance from stage 2. $\beta_0$ is the intercept and $\beta_d$, $\beta_w$, $\beta_m$ are slopes, all four fitted by ordinary least squares, which chooses them to minimise $\sum_t (y_t-\widehat{y}_t)^2$ over the training rows. HAR stands for Heterogeneous Autoregressive: the idea is that traders with daily, weekly and monthly horizons each contribute to tomorrow's volatility. The code uses only the three rv_cc columns (HAR_FEATURES), ignoring the other eleven predictors.

GARCH(1,1) — the volatility-clustering benchmark

            one_step_variance = (
                omega_decimal + self._alpha * observed_return**2 + self._beta * previous_variance
            )

            # For k>1, E_t[r_{t+k-1}^2] equals its conditional variance, so the
            # expected variance recursion uses persistence = alpha + beta.
            horizon_variance = one_step_variance
            variance_sum = one_step_variance
            for _ in range(1, self._forecast_horizon):
                horizon_variance = omega_decimal + persistence * horizon_variance
                variance_sum += horizon_variance

            average_variance_forecasts[row_index] = variance_sum / self._forecast_horizon
            previous_variance = one_step_variance
The formula the code implements

The model of daily return variance:

$$h_{t+1}=\omega+\alpha r_t^{2}+\beta h_t$$

Stepping further ahead, with $\phi=\alpha+\beta$:

$$h_{t+k}=\omega+\phi\,h_{t+k-1},\qquad k=2,\dots,H$$

And the forecast the code returns, matching the averaged target:

$$\widehat{y}_{t}=\frac{1}{H}\sum_{k=1}^{H}h_{t+k}$$

$h_{t}$ is the conditional variance of the return on day $t$, meaning the variance expected given everything known up to day $t-1$. $r_t$ is the daily log return on day $t$. $\omega$ is a constant floor, $\alpha$ is how strongly yesterday's shock raises today's variance, $\beta$ is how much of yesterday's variance carries over, and $\phi=\alpha+\beta$ is persistence, how slowly a volatility burst decays. $H$ is the forecast horizon, 1 or 5. GARCH stands for Generalized Autoregressive Conditional Heteroskedasticity; "heteroskedasticity" just means the variance is not constant over time.

Why the code multiplies returns by 100 and then divides by 10,000

fit passes returns * 100 to the arch library. Optimisers converge badly when the numbers they are fitting are around 0.01; scaling to percentage points puts them around 1. Variance scales with the square of the input, so every variance coming back out is divided by $100^2=10{,}000$ to return to decimal units. Get one of those two conversions wrong and GARCH's forecasts are off by a factor of ten thousand.

Ridge and Lasso — penalised linear models in log space

The formula

Both fit a straight line to the logarithm of variance, over all fourteen predictors after each has been standardised:

$$\log y_t \approx \gamma_0+\sum_{j=1}^{14}\gamma_j z_{j,t}, \qquad z_{j,t}=\frac{x_{j,t}-\bar{x}_j}{s_j}$$

Ridge chooses the coefficients by minimising

$$\sum_t\Big(\log y_t-\gamma_0-\sum_j \gamma_j z_{j,t}\Big)^{2}+\lambda\sum_j \gamma_j^{2}$$

Lasso replaces the penalty with the sum of absolute values:

$$\sum_t\Big(\log y_t-\gamma_0-\sum_j \gamma_j z_{j,t}\Big)^{2}+\lambda\sum_j \left|\gamma_j\right|$$

and the prediction is mapped back with

$$\widehat{y}_t=\max\left(e^{\widehat{\log y_t}},\,10^{-10}\right)$$

$x_{j,t}$ is predictor $j$ on row $t$; $\bar{x}_j$ and $s_j$ are its mean and standard deviation over the training rows, so $z_{j,t}$ is the standardised version. $\gamma_j$ are the fitted coefficients and $\gamma_0$ the intercept. $\lambda$ is the penalty strength, chosen automatically from 40 candidate values by RidgeCV or LassoCV using TimeSeriesSplit, which only ever validates on data later than what it trained on. Squaring the coefficients shrinks them all; taking absolute values drives some to exactly zero, which is why Lasso also selects variables.

Trap: fitting in logs shifts what is being predicted

Fitting $\log y$ and then taking $e^{\widehat{\log y}}$ does not give back an estimate of the average of $y$. It gives roughly the median of $y$, which for a right-skewed quantity like variance is lower than the mean. This is not an accident to be fixed — it is exactly why Ridge and Lasso top the QLIKE table and sit at the bottom of the MSE table. QLIKE rewards getting the typical day right; MSE is dominated by the few violent days these models under-forecast. Two scores, two different questions.

XGBoost — the nonlinear entry

What it does

Input: all fourteen predictors, unscaled and untransformed. Output: a variance forecast floored at $10^{-10}$. Role: the gradient-boosted decision tree entry, meant to catch relationships a straight line cannot. Its settings are fixed in the source: 200 trees, maximum depth 4, learning rate 0.05, and at least 10 rows per leaf.

It does not do what it appears to do

On this data XGBoost builds no splits at all. See the limitations section for the measurements.

07Stage 4 — walk-forward evaluation

This is the function that decides whether the whole benchmark is honest. It walks forward through time: train on the past, forecast the next block, move the boundary, repeat.

    # The target for feature row i averages realised variance over the horizon
    # trading days after i. Rows within horizon-1 of the first test date therefore
    # carry variance realised inside the forecast window, so they are purged from
    # the training slice. For horizon=1 nothing is purged.
    purged_train_rows = horizon - 1

    train_end_idx = _initial_train_end_index(working_df["date"], initial_train_years)
    train_end_idx = max(train_end_idx, MIN_TRAIN_OBS + purged_train_rows)
    ...
    retrain_points = list(range(train_end_idx, len(working_df), retrain_every_days))

    for point_idx, retrain_idx in enumerate(retrain_points):
        # Purge the last horizon-1 rows so no training target overlaps the test block.
        train_df = working_df.iloc[: retrain_idx - purged_train_rows]
In plain words

Hold back the first year. Fit every model on everything before the boundary, predict the next 21 trading days, then move the boundary 21 days forward and refit on the now-larger history. The training window only ever grows, and it never contains a day at or after the days being forecast.

What it does

Input: the 537-row feature table, a symbol, a horizon, and the config. Output: a long table with one row per date, per model, holding y_true and y_pred. Role: everything downstream — scores, statistical tests, diagnostics — reads only this table.

The purge, stated precisely

Training row $i$ carries the target $y_{i,H}=\frac{1}{H}\sum_{j=1}^{H}RV_{i+j}$, which is only fully known on day $i+H$. Let $T$ be the first forecast date. A training row is safe only when its label was already complete by $T$:

$$i+H\le T \iff i\le T-H$$

so rows $T-H+1,\dots,T-1$ must be removed — exactly $H-1$ rows.

$H$ is the horizon in trading days, 1 or 5. $T$ is the index of the first row in the test block. For $H=1$ the count is zero and nothing is dropped. For $H=5$, four rows are dropped from the end of every training window. Without this, the five-day model would be fitted on labels containing realised variance from days it is about to be asked to forecast.

Why the minimum training size adds the purged rows back

MIN_TRAIN_OBS + purged_train_rows rather than plain MIN_TRAIN_OBS. The constant is meant to guarantee at least 25 rows actually reaching the model. Since $H-1$ rows are removed after the boundary is chosen, the boundary has to sit $H-1$ rows later to leave 25 behind. It also keeps retrain_idx - purged_train_rows from ever going negative.

Sample data
out — the schedule actually used 
feature rows                537   (2022-11-02 to 2024-12-20)
first feature date          2022-11-02
cutoff = first + 1 year     2023-11-02
first test row index        251
first test date             2023-11-02

For horizon 1, the first model is fitted on rows 0 to 250 and forecasts rows 251 to 271. For horizon 5, the same block is fitted on rows 0 to 246 — four rows shorter — and forecasts the same 21 dates. Every model produces 286 forecasts at each horizon, so forecasts.parquet holds $5\times2\times286=2{,}860$ rows.

Trap: a failing model becomes a silent row of NaN

The fit and predict call is wrapped in except Exception. A model that throws is logged at warning level and its whole forecast block is filled with NaN. Nothing crashes. If you are reading only the scoreboard, a model that failed on some blocks looks identical to one that succeeded, just with fewer scored observations — and compute_scores silently skips any model with fewer than 10 valid rows, so a fully broken model vanishes from the table entirely rather than appearing as a failure. Always read the n_obs column, and check the log.

08Scoring — QLIKE, MSE, Diebold-Mariano

The two loss functions

The formulas the code implements

Mean squared error, from mse_loss:

$$\text{MSE}=\frac{1}{n}\sum_{t=1}^{n}\left(y_t-\widehat{y}_t\right)^{2}$$

Quasi-likelihood loss, from qlike_loss:

$$\text{QLIKE}=\frac{1}{n}\sum_{t=1}^{n}\left[\log\widehat{y}_t+\frac{y_t}{\widehat{y}_t}\right]$$

$y_t$ is the realised variance on scored date $t$ and $\widehat{y}_t$ the forecast, both strictly positive daily variances; $n$ is the number of scored dates, 286 here. Lower is better for both. Note what the code does not include: the textbook QLIKE usually carries a $-\log y_t - 1$ term that makes its minimum zero. Those terms do not depend on the forecast, so dropping them does not change any ranking — but it does mean the printed QLIKE values are large negative numbers near $-8.8$ rather than small positive ones, and they are only comparable within this project.

Why QLIKE is the primary score for variance

MSE works in squared variance units. Daily variance here is around $10^{-4}$, so squared errors are around $10^{-9}$, and the total is dominated almost entirely by a handful of turbulent days. QLIKE instead depends on the ratio $y_t/\widehat{y}_t$, so being twice too high on a calm day costs the same as being twice too high on a wild day. It also punishes under-forecasting harder than over-forecasting, which is the asymmetry a risk manager wants.

Sample data
in — HAR-RV, first scored date 
date    2023-11-02

diebold_mariano_test — is the gap real?

In plain words

Model A beat model B on average. But forecast errors wander together from day to day, so a run of luck can look like skill. This test asks whether the average gap is big compared to how much it bounces around.

The formula the code implements

Let $d_t=L^A_t-L^B_t$ be the difference in QLIKE loss on date $t$, and $\bar{d}$ its average. The long-run variance uses Bartlett-weighted autocovariances:

$$\widehat{\gamma}_k=\frac{1}{n}\sum_{t=k+1}^{n}(d_t-\bar{d})(d_{t-k}-\bar{d})$$

$$\widehat{V}=\widehat{\gamma}_0+2\sum_{k=1}^{K}\left(1-\frac{k}{K+1}\right)\widehat{\gamma}_k, \qquad K=\max\left(1,\left\lfloor n^{1/3}\right\rfloor\right)$$

$$\text{DM}=\frac{\bar{d}}{\sqrt{\widehat{V}/n}},\qquad p=2\left[1-\Phi(\left|\text{DM}\right|)\right]$$

$L^A_t$ and $L^B_t$ are the per-day QLIKE losses of the two models. $n$ is the number of common dates, 286 here. $\widehat{\gamma}_k$ is the autocovariance of the loss difference at lag $k$: how much today's gap resembles the gap $k$ days ago. $K$ is the bandwidth, how many lags are counted; at $n=286$ it evaluates to 6. The Bartlett weights $1-k/(K+1)$ taper smoothly to zero so that $\widehat{V}$ cannot come out negative. $\Phi$ is the standard normal cumulative distribution function. A positive DM statistic means model A had the higher average loss, so model A is the worse one.

Why the autocovariance terms are needed at all

If losses were independent day to day, $\widehat{\gamma}_0/n$ would be the right variance. They are not: volatility comes in clusters, so a model that is too low today is usually too low tomorrow. Ignoring that would make the standard error too small and every p-value too impressive. The Bartlett-weighted sum is the standard correction.

13Honest limitations

XGBoost is not really in the contest

On this data, XGBoost fits zero splits. Measured directly on the first training block: all fourteen feature importances come back as 0.0, and the model returns a single constant, 0.00010017, for all 21 test rows — which is essentially the training target mean of 0.00009958. Across all 286 forecast dates there are only 14 distinct predictions, one per retrain block.

The cause is the scale of the target. Daily variance is around $10^{-4}$, so the split gains XGBoost computes fall below the threshold at which it will grow a tree. Re-running the identical model with the target multiplied by 100 or more makes it use all fourteen features and produce 20 distinct predictions per block:

target scale    1e+00: unique preds  1/21, features used  0/14, pred std 0.000e+00
target scale    1e+02: unique preds 20/21, features used 14/14, pred std 1.241e-05
target scale    1e+04: unique preds 20/21, features used 14/14, pred std 1.234e-05
target scale    1e+06: unique preds 20/21, features used 14/14, pred std 1.234e-05

This matters for how the results are read. "XGBoost is significantly worse than HAR-RV, Ridge and Lasso at $p<0.0001$" is not a finding about gradient boosting. It is the finding that those three models beat a constant. This was left unchanged rather than silently fixed, because scaling or log-transforming the target is a modelling decision that changes the benchmark's headline result, and that is the owner's call. The one-line change would be to give XGBoostModel the same log-target transform that RidgeModel and LassoModel already use.

GARCH fits alpha to zero and becomes nearly flat

On the first training block the fitted parameters are $\omega=0.014878$, $\alpha=0.000000$, $\beta=0.973339$. With $\alpha=0$ the model has no reaction to individual return shocks left; it is a slowly decaying average with persistence 0.973. Its forecasts over the first eight days move from 0.00005604 to 0.00005600, and its full 286-day range is 0.000038 to 0.000134, against HAR-RV's 0.000036 to 0.000249. This is what the optimiser chose on roughly one year of daily returns; it is a real result on this sample, not a coding error, but it means the GARCH column is closer to a slowly drifting constant than to the textbook volatility-clustering model.

The models do not all see the same information

Every predictor built in stage 3 is lagged to day $t-1$: the HAR columns use .shift(1), and options and VIX are moved forward a business day. So on row $t$, HAR-RV, Ridge, Lasso and XGBoost forecast $RV_{t+1}$ knowing nothing after day $t-1$ — effectively a two-day-ahead forecast wearing a one-day label.

GARCH is different. Its predict loop consumes daily_returns on row $t$ itself, so it forecasts $RV_{t+1}$ knowing the day-$t$ return. That is not look-ahead — the day-$t$ return is known at the day-$t$ close, before $RV_{t+1}$ happens — but it is one extra day of information that the other four do not get. The comparison is therefore tilted slightly in GARCH's favour. Levelling it would mean either lagging GARCH's return input or un-lagging the realised variance columns; both change the benchmark's numbers, so this is documented rather than altered.

The bandwidth rule can be too small for the five-day test

Five-day targets overlap: consecutive rows share four of their five days, so loss differences are autocorrelated out to lag 4 by construction. A Diebold-Mariano test needs at least $H-1=4$ lags to account for that. The code uses $K=\lfloor n^{1/3}\rfloor$, which at $n=286$ gives 6 — comfortably enough. But the rule does not know the horizon: at $n=30$, the minimum this code will test, it gives $K=3$, which is too few, and the resulting p-values would be too small. Safe at the shipped configuration, fragile at a shorter one.

One asset, 286 days, and no transaction costs

The whole benchmark rests on SPY over roughly fourteen months of out-of-sample dates, spanning one volatility regime. The robustness_symbols setting exists but ships empty. Nothing here is evidence that a ranking holds for another asset, another period, or a stress episode. The Diebold-Mariano table already says most pairs are indistinguishable at this sample size.

One worry that measured smaller than expected

The target is built from intraday minute returns and so omits the overnight price jump, while GARCH is fitted on close-to-close daily returns that include it. In principle GARCH would then be forecasting a larger quantity than the one being scored. Measured on this data, the gap is small: the mean of rv_cc is 8.556844e-05 and the variance of the daily log returns is 8.518606e-05, a ratio of 0.9955. The reason is that these minute bars run 04:00 to 19:59, capturing sixteen hours of the day, so very little movement is left outside the window. Worth re-checking if the data source is ever changed to regular trading hours only.

14Fixes applied

Three changes to src/volcast/evaluation/train_evaluate.py. No other source file was modified. The full test suite, 56 tests, passes before and after.

1. Purge overlapping targets from the training window

The bug

For the five-day horizon, the training window ran right up to the first forecast date. The last four training rows carried targets averaging realised variance over days that fall inside the block being forecast. Those labels were not knowable at the forecast origin, so the fitted parameters had seen the future. This is genuine look-ahead bias, and it affected only horizon 5.

# before
train_df = working_df.iloc[:retrain_idx]

# after
purged_train_rows = horizon - 1
train_df = working_df.iloc[: retrain_idx - purged_train_rows]

The minimum training size was raised to MIN_TRAIN_OBS + purged_train_rows so that 25 rows still reach the model after the purge, and so the slice index cannot go negative. Horizon 1 is unaffected, since $H-1=0$.

2. Advance the GARCH variance state up to the forecast date

The bug

GARCHModel.predict seeds its recursion with the last fitted conditional variance. Its own loop invariant needs that seed to be $h_t$ for the first row it is given. What it received was $h_T$, the conditional variance of the last training row. Those are one row apart for horizon 1, and after fix 1, five rows apart for horizon 5. Every retrain block therefore started from a stale variance state.

The alignment was confirmed by experiment rather than assumed. Fitting a simulated GARCH series and reconstructing the last conditional variance two ways: $\omega+\alpha r_{T-1}^{2}+\beta h_{T-1}$ reproduces conditional_volatility[-1] to sixteen digits, while $\omega+\alpha r_{T}^{2}+\beta h_{T-1}$ does not. So the library's $h_t$ is indexed to the return on day $t$, and the code needed one more update step.

# before
return model.predict(test_df[garch_columns]), model.name

# after: feed the last training row and any purged rows as warm-up,
# then keep only the tail that lines up with test_df
state_predictions = model.predict(garch_state_df[garch_columns])
return state_predictions[-len(test_df) :], model.name

The warm-up frame is built by the caller, which is the only place that knows the row indices:

last_train_idx = retrain_idx - purged_train_rows - 1
garch_state_df = working_df.iloc[last_train_idx:test_end]

Only GARCH's numbers moved: horizon 1 QLIKE went from $-8.761820$ to $-8.762988$, horizon 5 from $-8.753833$ to $-8.752250$. Small, as expected for a one-step state correction that decays at $\beta=0.97$ — but it is now correct rather than approximately correct.

3. Read the Diebold-Mariano model list off the pivot table

The bug

compute_dm_tests took its model list from the raw forecast table, then looked each name up in a pivot table. If a model failed at every retrain point, its forecasts are all NaN, pivot_table drops the column, and the lookup raised KeyError — killing stage 4 after the forecasts had been computed but before anything was written. A latent crash, reachable whenever one model breaks, which the except Exception handler makes easy.

# after: the pivot is the authority on which models actually have forecasts
models = sorted(pivot["y_pred"].columns)
What was deliberately left alone

Nine files in this repository carry uncommitted formatting-only changes from an automated ruff format pass — quote style, line wrapping, import ordering, and two redundant int() calls around len(). Each hunk was inspected. None removes an import that is still in use, and the test suite passes, so none of them were committed. The limitations in section 13 were documented rather than changed, because each one would alter the benchmark's reported ranking, which is a research decision rather than a bug fix.
